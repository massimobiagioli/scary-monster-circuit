# ADR-0012: Bootable flash image and reliable USB enumeration

- **Status:** Accepted
- **Date:** 2026-10-11

## Context

After the USB workflow was added (ADR-0010, ADR-0011), flashing "worked" but
the board stayed in the Boot ROM: on a normal power-up it never ran the
firmware, and no USB serial port appeared.

Inspecting the built image showed why: `.boot2` was linked at `0x10003a20`
instead of `0x10000000`. The RP2040 Boot ROM jumps to the very start of flash,
expects the second-stage boot loader there, and finds nothing, so it falls back
to USB bootloader mode. `firmware/memory.x` declared the `BOOT2` region but
never placed `.boot2` in it.

Even once the image booted, the USB device did not enumerate on macOS: USB needs
to be polled often, and the RP2040 has a known errata (RP2040-E5) where the USB
device can fail to leave reset on a busy USB bus.

## Decision

- Fix `firmware/memory.x` so `.boot2` sits at the start of flash, matching the
  rp-hal template:
  - `EXTERN(BOOT2_FIRMWARE)` pulls in the board crate's boot code.
  - `SECTIONS { .boot2 ... } INSERT BEFORE .text` places it at `ORIGIN(BOOT2)`,
    so `.vector_table` lands at `0x10000100`.
- Enable the `rp2040-e5` feature of `rp-pico` to work around the USB errata.
- Poll the USB stack every millisecond (`Logger::idle`) instead of once per
  50 ms loop, and spend the first second polling so the host can enumerate the
  device before the slower main loop begins.

## Consequences

- The firmware actually boots from flash and enumerates as a USB serial port;
  `make logs` and `make probe` work with nothing but a USB cable.
- `make upload-firmware` now produces a runnable image; the Boot ROM leaves
  bootloader mode on its own after flashing.
- USB is serviced frequently, which costs a few cycles but keeps enumeration and
  the serial port reliable.
- The `rp2040-e5` workaround briefly borrows GPIO15 during a USB reset; the prop
  uses GPIO16 for the servo, so there is no conflict.
