# ADR-0011: Logs over USB serial instead of RTT

- **Status:** Accepted
- **Date:** 2026-10-11

## Context

Flashing now works over USB (ADR-0010), but the runtime logs still used `defmt`
over RTT, which only a SWD debug probe can read. On the single-USB-cable setup
`make logs` therefore failed with "No connected probes were found". The logs
have to travel over the same USB cable that is already used for flashing, so a
developer with only a Pico and a cable can see what the firmware is doing.

## Decision

- Replace `defmt` + `defmt-rtt` with a USB CDC serial port built from
  `usb-device` + `usbd-serial`, polled in the main loop.
- Add a small `Logger` in `firmware/src/main.rs` that owns the USB device and
  the serial port. It formats log lines with `core::fmt` into a fixed stack
  buffer and writes them best-effort, only while a host has the port open
  (`DTR`), greeting it with a banner so the logs are never empty.
- `make logs` finds the USB serial port (`/dev/cu.usbmodem*` on macOS,
  `/dev/ttyACM*` on Linux) and streams it. `make probe` flashes the `probe`
  build and streams the dashboard over the same port.
- Add a `build` Makefile target (`FEATURES=probe` for the dashboard build) and
  have both `upload-firmware` and `probe` call it, so the firmware is always
  built through one command.
- Drop the `-Tdefmt.x` linker flag and the `DEFMT_LOG` environment variable.

## Consequences

- `make logs` works with nothing but the USB cable; no debug probe and no
  `defmt`/RTT are needed.
- `probe-rs` is now optional and only used to flash over SWD for owners of a
  debug probe; nothing in the normal workflow calls it.
- The USB stack must be polled from the main loop, and logging is best-effort:
  bytes written while no host is reading are dropped rather than buffered.
- This supersedes the RTT transport of ADR-0008; the `probe` dashboard itself
  still exists, now streamed over USB serial.
